Architecture

The SmartCart candidate is a local SwiftUI app with observable state, explicit retailer capabilities, versioned persistence, and a separate local-only backend reference.

On this pageCritical pathLayersStateRetailer boundaryPersistenceLocal backendData flowExtension gates
Boundary: this document describes the checked-in demo architecture. It does not assert production security, scale, cloud services, retailer approval, or live commerce readiness.

Supported critical path

Import recipe → review and edit ingredients → scale servings → mark pantry status → apply preferences → choose one prototype store → resolve seeded products or search fallbacks → confirm and save manifest → open guided retailer destinations.

Conceptual layers

SwiftUI presentation

Feature views render the import, recipe, cart, retailer, handoff, and preference experiences. Shared components and theme values keep interaction states consistent.

Application state

AppModel coordinates the active recipe, preferences, stores, shopping items, manifests, navigation state, retailer service, and persistence store.

Domain models

Recipe, ingredient, package, preference, product-record, manifest, fulfillment, source, and capability types make uncertain data explicit.

Services

Protocols separate retailer lookup and persistence from views. The candidate supplies a demo catalog service and a local JSON state store.

Local reference backend

A separate zero-dependency Node.js service demonstrates mock auth, manifests, analytics ingestion, caching, OAuth state, and affiliate abstraction entirely in local/demo mode.

State and dependency seams

AppModel receives a SmartCartStateStoring implementation and a RetailerCatalogService implementation. Default construction uses JSONSmartCartStateStore and DemoWalmartCatalogService. In-memory storage supports focused tests.

Many user-facing state properties persist on change after initialization. This keeps the beta straightforward, but future production work should measure write frequency, define concurrency behavior, and document failure recovery before promising durability guarantees.

Retailer service boundary

The protocol exposes catalog search, product resolution, refresh, and handoff creation, while a capability set communicates what an adapter supports. The demo adapter advertises local catalog search, exact product links, pickup and delivery eligibility metadata, and guided product handoff. Its live refresh method returns an unsupported-capability error.

Versioned persistence

The default store writes state.json in the app’s Application Support area. Schema version 2 is current in the unreleased candidate. The store can migrate legacy schemas 0 and 1 and quarantine corrupt state rather than silently treating it as valid. Version 2 adds pantry inventory, preferred product IDs, and bounded local diagnostic events. The test suite covers migration, relaunch, and corruption behavior.

Local reference backend

The repository’s backend directory is a credential-free Node.js ESM reference service for local development and automated tests. It binds to loopback by default, has no package dependencies, and labels JSON responses as local-demo.

  • Mock accounts and bearer sessions exist only in process memory.
  • OAuth validates local state and PKCE mechanics but performs no provider request or token exchange.
  • Manifests and diagnostic events disappear on restart.
  • Product and catalog fields are client-supplied demo values, never live retailer data.
  • Affiliate-link decoration is deterministic demo behavior with no live attribution or approved program.
  • Rate limiting, caching, and redacted logs are development safeguards, not production infrastructure.

Nothing in this static site calls that service, and its presence does not establish cloud sync, hosted accounts, production authentication, or a retailer connection.

Current data flow

  1. Camera or photo import uses iOS permission surfaces and Apple Vision text recognition.
  2. Pasted text and recognized ingredients become local application models.
  3. Recipe-page import requests a third-party page and extracts supported recipe metadata when available.
  4. Barcode scanning on supported devices resolves only against a bundled offline demo cache.
  5. Product matching operates against seeded demo records in the current adapter.
  6. Opening a product or search leaves SmartCart for a third-party retailer destination.
  7. Application state, pantry data, and bounded tester events are saved locally as versioned JSON.
  8. The optional reference backend remains a separately started local process with in-memory demo state.

Hosted telemetry, production authentication, cloud sync, provider OAuth, live affiliate attribution, and live catalog refresh are not part of the current candidate. Adding any of them changes the public privacy and architecture story.

Gates before widening the system

  • Implement and test adapter capability truth; never infer a working integration from model enum cases.
  • Define credentials, authentication, secrets, rate limits, retries, observability, and vendor failure modes.
  • Preserve explicit provenance, observation time, and fallback labels across all catalog sources.
  • Review data minimization, retention, deletion, encryption, logging, consent, and third-party disclosures.
  • Add end-to-end evidence for cart, reservation, payment, or order claims before changing marketing copy.
  • Update legal drafts and affiliate disclosures before introducing tracking or compensation.
